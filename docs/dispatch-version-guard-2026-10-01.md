## 安全失效规则

- Web、KOOK、Discord 共用接单服务，缺失、null、字符串、负数、小数、不安全整数或不匹配的 dispatchVersion 均拒绝。没有读取数据库当前版本来补齐缺失请求的分支；订单锁内核对版本、状态、指定主体及原有资格/占用。
- **所有无版本历史卡片均失效，包括当前订单仍为版本 0 的情况。** 新卡片始终为 `order.accept.<id>.<version>`，版本 0 明写 `.0`。KOOK / Discord 严格解析整个按钮值，额外后缀、科学计数法、前导零及尾随换行不被当作合法版本。
- KOOK 仍先持久入队并 ACK；工作进程拒绝旧卡后只给点击人发送“派单卡片已失效，请刷新订单后重试”，不接单。提示使用既有持久发送凭据与 UNKNOWN 保护，丢 ACK 不自动重复发送。Discord 返回仅点击人可见的提示。直接 API 返回 400 和刷新提示。
- 指定派单、切换模式、拒接也必须携带用户当时看到的 dispatchVersion；拒绝缺失/过期版本。到期任务必须包含版本；客服批量到期处理先读取每单版本，再在锁内核对，旧任务不能影响新分配。
- 已执行的同一管理员、同一版本来源、同一分配内容/期限和同一原因的命令重投，只返回已执行结果，不再次派单或扣款；不同管理员、不同内容或更旧轮命令不能借此改写当前分配。审计保存 requestedVersion 以核对这一重投。

后台派单页面、陪玩接单/拒接页面、草稿转正式单、Discord / KOOK 卡片生产者均传递显式版本。未改佣金、结算、退款、投诉冻结、提现、队列重试或 UNKNOWN 核对规则；不新增数据库迁移。

## API 协议与独立复测

下列请求需显式增加数字字段 `dispatchVersion`，值取此前读取的订单/派单结果。未升级的调用方会安全失败，不能依赖旧的省略行为：

- `PATCH /api/admin/orders/:id/assign`
- `PATCH /api/admin/orders/:id/dispatch`
- `PATCH /api/orders/:id/accept`、`.../:id/decline`
- `POST /api/kook/orders/accept`、`POST /api/discord/orders/accept`

独立 QA 文件与预期完全未改。复测作者需按以上协议更新合法请求夹具，仍保留所有资金/权限/状态期望。R18 应使用历史已保存的无版本动作字符串作为升级夹具；新生成的版本 0 卡片现在应断言带 `.0`，不能继续把新版生成器当成旧版生成器。无版本历史动作最终保持 ASSIGNED 的原 R18 业务期望不变。

旧通知保存的请求正文、SENT 回执和 UNKNOWN 状态没有被改写，也没有自动补发。用户可刷新陪玩端读取当前订单并用显式版本操作；需要新一轮分配时由客服明确处理。真实历史群消息、平台权限与回调仍未访问。
